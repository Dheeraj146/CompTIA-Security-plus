# Domain 4 — Module 16: Security Data Sources and Analysis

Security operations depend on telemetry. A SOC cannot investigate an alert effectively if it cannot determine what happened, when it happened, which account or asset was involved, what happened next, and whether the activity occurred elsewhere.

Security data comes from endpoints, networks, identity systems, applications, cloud platforms, email, and security controls. No single source provides complete visibility.

A useful model is:

**Source → Collect → Normalize → Correlate → Analyze → Validate → Scope → Detect → Respond**

# 1. Security Telemetry

Security telemetry is data generated by systems and security controls that can help identify and investigate security-relevant activity.

Examples include process creation, authentication attempts, file changes, DNS queries, firewall decisions, network connections, application requests, cloud API calls, EDR detections, VPN sessions, and email-security events.

Telemetry is the raw material used by SOC analysts, SIEM platforms, detection systems, threat hunters, and incident responders.

# 2. Why Multiple Data Sources Are Necessary

Consider a suspicious login. An identity log may show a successful login, source IP, and timestamp, but it may not show what the user did afterward.

An analyst can correlate identity logs with VPN, endpoint, DNS, firewall, proxy, cloud, and application telemetry to reconstruct the sequence:

```text
Identity Log → VPN → Endpoint → DNS → Firewall/Proxy → Cloud/Application
```

The combined evidence is much more useful than any individual record.

# 3. Endpoint Telemetry

Endpoint data comes from workstations, servers, laptops, virtual machines, EDR agents, antivirus, and operating-system logs.

Important events include process creation, parent-child relationships, command lines, logons, file creation/modification/deletion, registry changes, services, scheduled tasks, device connections, network connections, and security detections.

Endpoint telemetry is especially useful for determining what actually executed on a host.

## Process and Command-Line Analysis

Process trees reveal execution chains such as:

```text
explorer.exe
   └── winword.exe
        └── powershell.exe
             └── suspicious.exe
```

Investigate the parent process, child process, user context, command line, executable path, hash, start time, and network connections. A process name alone is weak evidence because legitimate tools can be abused or renamed.

Command-line telemetry can reveal discovery, scripting, downloads, persistence, and administrative activity. Context is essential because legitimate administrators also use tools such as PowerShell and cmd.exe.

## File and Registry Data

File telemetry can reveal dropped malware, scripts, temporary files, sensitive-data staging, and mass file modification. Registry/configuration telemetry can reveal persistence and security-setting changes. Correlate these changes with the process and user that caused them.

# 4. Network Telemetry

Common network sources include firewall logs, router and switch telemetry, IDS/IPS, proxies, DNS, VPN, NetFlow/IPFIX, PCAP, and wireless logs.

Network telemetry can identify scanning, command and control, lateral movement, data exfiltration, suspicious destinations, unexpected protocols, and policy violations.

## PCAP

Packet capture provides detailed packet-level evidence such as source/destination addresses, ports, protocols, TCP behavior, and payload information where available. It is powerful for focused investigation but can produce very large volumes of data.

## NetFlow/IPFIX

Flow telemetry summarizes communications using fields such as source/destination IP, ports, protocol, timestamps, duration, packets, and bytes.

| PCAP | NetFlow/IPFIX |
|---|---|
| Packet-level detail | Flow metadata |
| Potential payload visibility | Normally no full payload |
| Large storage requirement | Generally smaller |
| Deep protocol investigation | Traffic-pattern analysis |

## DNS Logs

DNS logs can reveal requested domains, timestamps, clients, query types, and responses. They are useful for investigating malware infrastructure, suspicious domains, and possible DNS tunneling.

## Firewall and Proxy Logs

Firewall logs can show source, destination, port, protocol, action, timestamp, and rule. A denied connection attempt is not equivalent to confirmed successful communication.

Proxy logs can show users, destinations, URLs, methods, response codes, and transferred bytes, helping investigate malicious downloads, phishing, C2, and web-based exfiltration.

## VPN and Wireless Logs

VPN telemetry can show usernames, source addresses, authentication results, connection times, and assigned addresses. Wireless telemetry can show authentication, association, access-point, client, 802.1X, and rogue-AP events.

# 5. Identity and Authentication Data

Identity systems provide successful and failed authentication, MFA, password changes, account creation/disablement, group membership, privilege changes, service-account activity, and federation events.

Authentication answers **who authenticated?** Authorization answers **what was that identity allowed to access or perform?** Both may be required to establish whether unauthorized access occurred.

## Active Directory Data

In Windows environments, useful evidence includes account logons, failed authentication, privileged-group changes, account creation, password changes, group membership, Kerberos-related activity, and administrative actions.

A sequence such as:

```text
Privileged-group change → Successful authentication → Administrative activity
```

may warrant investigation depending on authorization, timing, account role, and other evidence.

# 6. Application and Database Data

Application logs can reveal authentication, authorization, transactions, API requests, errors, administrative actions, and configuration changes.

Web-server logs may contain client IP, timestamp, HTTP method, resource, status code, user agent, and response size. These can help investigate scanning, authentication abuse, and exploitation attempts.

Database logs can reveal authentication, queries, administrative actions, permission changes, and data access. They are important in investigations involving unauthorized access, privilege abuse, or data theft.

# 7. Email Security Data

Email systems and security gateways can provide sender, recipient, message identifiers, attachment information, URLs, delivery status, authentication results, and malware/phishing detections.

This can help determine who received a malicious message, whether an attachment was delivered, and whether similar messages affected additional users.

# 8. Cloud Audit Data

Cloud audit logs can record API calls, identity activity, resource creation/deletion, configuration changes, permission changes, storage access, and network changes.

A useful investigation might correlate:

```text
Cloud Identity
   ↓
Privilege Change
   ↓
New Resource
   ↓
Security-Group Change
   ↓
Sensitive Storage Access
```

## Control Plane vs Data Plane

The control/management plane manages cloud resources, such as creating a VM or changing IAM permissions. The data plane uses the service itself, such as reading objects from storage or querying a database. Investigations may require telemetry from both.

# 9. Security-Control Telemetry

Security technologies generate valuable data, including EDR, IDS/IPS, antivirus, WAF, DLP, NAC, vulnerability-scanner, and email-security events.

These detections are evidence, not infallible truth. False positives, false negatives, incomplete context, and sensor failures must be considered.

# 10. Severity and Context

Logs may use severity levels such as informational, warning, error, and critical. Severity does not automatically equal incident priority.

A critical application error may not be a security incident, while an ordinary authentication event can become highly significant when correlated with suspicious activity.

# 11. Normalization

Different systems may represent the same field differently:

```text
Firewall: src=10.1.1.5
EDR: source_ip=10.1.1.5
Cloud: clientAddress=10.1.1.5
```

Normalization maps these into a common structure, making cross-source searches and correlation easier.

# 12. Time Synchronization

Accurate timestamps are essential for investigation. Inconsistent clocks can produce an incorrect event sequence and therefore an incorrect incident timeline.

Centralized time synchronization such as NTP supports SIEM correlation, incident reconstruction, and forensics.

# 13. Event Correlation

Correlation connects related events across sources:

```text
Failed Logins → Successful Login → VPN → Privileged Action → Process → External Connection
```

No individual event necessarily proves compromise. The sequence can provide stronger evidence and reveal an attack path.

# 14. Baselines and Behavioral Analysis

A baseline represents expected behavior for a user, system, network, or application. Examples include normal login times, destinations, data volumes, and administrative activity.

An anomaly is a deviation from the baseline, but an anomaly is not automatically malicious. Analysts must consider role, timing, business context, and authorization.

# 15. Indicators vs Confirmed Findings

An indicator is evidence suggesting that something may be wrong. A confirmed finding requires sufficient validation.

For example, a known malicious IP in firewall logs is important, but the analyst should determine whether traffic was allowed, which host communicated, whether communication succeeded, and what happened before and after it.

Avoid treating a single indicator as automatic proof of compromise.

# 16. Timeline Analysis

Timeline analysis organizes events chronologically:

```text
09:12 Phishing email delivered
09:18 Attachment opened
09:18 Office launches PowerShell
09:19 Malicious process created
09:20 DNS query
09:20 Outbound connection
09:31 Lateral authentication
```

This can help establish initial access, execution, persistence, credential access, lateral movement, C2, and other stages when supported by evidence.

# 17. Pivoting and Enrichment

Analysts pivot from one indicator to related evidence. For example:

```text
Suspicious IP
   ↓
Internal hosts communicating with it
   ↓
Associated domains
   ↓
Processes making connections
   ↓
Users running processes
   ↓
Related authentication events
```

Enrichment adds context such as reputation, ASN, geolocation, historical observations, or malware-family information. Enrichment improves context but does not replace validation.

# 18. Data Quality and Visibility Gaps

Security analysis can be undermined by missing logs, incorrect timestamps, incomplete fields, parsing errors, duplicate events, sensor outages, retention gaps, or logs that are generated but never collected.

If an EDR agent stopped reporting three days ago, the absence of EDR alerts does not prove the endpoint was clean. It means visibility is degraded.

**No evidence of malicious activity is not necessarily evidence of no malicious activity when telemetry is missing.**

SOC teams should monitor the health of their telemetry pipeline as well as the events flowing through it.

# 19. SIEM Correlation

A SIEM can combine identity, VPN, endpoint, DNS, firewall, proxy, cloud, and application telemetry to support centralized search, correlation, alerting, investigation, and reporting.

The analyst should understand what each source can prove rather than assuming that SIEM correlation makes every alert automatically accurate.

# 20. Choosing the Right Data Source

| Question | Useful source |
|---|---|
| Who logged in? | Identity/authentication logs |
| What executed? | Endpoint/EDR |
| Where did a host connect? | Firewall/flow/EDR/proxy |
| What domain was queried? | DNS |
| Was web traffic allowed? | Proxy/firewall |
| What cloud configuration changed? | Cloud audit logs |
| What application action occurred? | Application logs |
| What happened at packet level? | PCAP |
| Was a malicious file detected? | EDR/AV |
| Who received phishing email? | Email-security logs |

The best investigation often combines several sources.

# 21. Scenario — Compromised Account

A user authenticates from an unusual source. Correlate identity logs with MFA, VPN, endpoint, cloud, and network activity. The goal is to determine whether the login was merely unusual or part of unauthorized activity.

# 22. Scenario — Malware C2

An EDR alert identifies a suspicious process. Pivot from process to command line, hash, network connection, DNS query, destination IP, firewall history, and other hosts. This helps determine C2 behavior and scope.

# 23. Scenario — Data Exfiltration

A server sends an unusually large amount of outbound data. Examine flow volume, firewall/proxy connections, DNS destinations, endpoint processes, application data access, and the responsible identity. The objective is to connect **data access + process + identity + destination + transfer volume**.

# 24. Common Analysis Failures

### Relying on one source

A single source rarely provides the whole attack story. Correlate relevant telemetry.

### Ignoring time synchronization

Incorrect timestamps produce incorrect timelines. Maintain reliable time synchronization.

### Treating an indicator as proof

Validate suspicious hashes, IPs, domains, and events with additional evidence.

### Ignoring telemetry health

A silent sensor can create a blind spot. Monitor collection pipelines and agent health.

### Collecting everything without purpose

Excessive irrelevant data increases cost and analyst workload. Collect according to security and business requirements.

### Ignoring context

Unusual activity is not automatically malicious. Evaluate user role, asset, timing, location, baseline, and authorization.

# 25. Security+ Exam Distinctions

### PCAP vs NetFlow/IPFIX

- **PCAP:** detailed packet-level evidence.
- **Flow:** summarized communication metadata.

### Authentication vs Authorization

- **Authentication:** verifies identity.
- **Authorization:** determines permitted access/actions.

### Event vs Alert

- **Event:** recorded occurrence.
- **Alert:** event or correlation meeting a detection condition and requiring attention.

### Indicator vs Finding

- **Indicator:** clue suggesting suspicious activity.
- **Finding:** conclusion supported by analysis and evidence.

### Baseline vs Anomaly

- **Baseline:** expected behavior.
- **Anomaly:** deviation from expected behavior; not automatically malicious.

### Collection vs Analysis

- **Collection:** obtaining telemetry.
- **Analysis:** interpreting and correlating telemetry.

# 26. Security+ Decision Framework

When analyzing a security-data question:

1. **Define the question.** What must be established?
2. **Select the source.** Which system records that activity?
3. **Check data quality.** Are timestamps, fields, and collection functioning correctly?
4. **Corroborate.** What independent source can support the event?
5. **Build the timeline.** What happened before and after?
6. **Compare the baseline.** Is the activity expected?
7. **Validate.** Is this an indicator or a confirmed finding?
8. **Determine scope.** Which users, hosts, processes, domains, IPs, or cloud resources are related?
9. **Document and act.** Escalate, detect, contain, or continue investigation according to the evidence.

```text

        ↓

        ↓

        ↓

        ↓

        ↓

```

# 28. Key Takeaways

- Security operations depend on reliable telemetry.
- No single data source provides complete visibility.
- Endpoint telemetry reveals process, file, registry, and host activity.
- Network telemetry reveals communication and traffic patterns.
- PCAP provides packet-level evidence; NetFlow/IPFIX provides flow metadata.
- DNS, firewall, proxy, VPN, and wireless logs answer different network-security questions.
- Identity logs are essential for account-compromise investigations.
- Application and database logs reveal activity infrastructure telemetry may miss.
- Cloud audit logs reveal management-plane and service activity.
- Authentication verifies identity; authorization determines permitted access.
- Normalization makes cross-source correlation easier.
- Accurate time synchronization is essential for timeline reconstruction.
- Baselines help identify deviations, but anomalies are not automatically malicious.
- Indicators should be validated with additional evidence.
- Analysts pivot from one indicator to related users, hosts, processes, domains, and connections.
- Missing telemetry creates visibility gaps and must not be interpreted as proof that no malicious activity occurred.
- SIEM platforms help correlate multiple telemetry sources, but analysts still need to validate findings.
- Effective analysis combines endpoint, network, identity, application, cloud, email, and security-control telemetry according to the investigation question.

## Core Security+ Mental Model

**Ask → Identify Evidence → Select Source → Collect → Normalize → Correlate → Timeline → Baseline → Validate → Scope → Respond**

The central principle is: **understand what each telemetry source can establish, correlate independent evidence, account for visibility gaps, and never confuse an isolated indicator or anomaly with confirmed compromise without validation.**
